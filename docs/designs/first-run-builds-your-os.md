# Design: Membrae first run that builds your OS for you

## Problem Statement

Membrae is a personal OS: projects and life in one place, readable and writable by the user and their agents. Today it works for one person, its author. A second person who opens it meets an empty app with a sidebar of nouns (Projects, Tasks, Spaces, Runs) and no starting point. "Everything in one place" cannot be felt in an empty app, so the claim is untestable until the app fills itself.

This design covers the first five to ten minutes for a new user: install, a setup conversation that builds their first project and first Space from material they already have, a review step, and connecting their coding agent.

## Demand Evidence

None outside the founder. Stated in session: "Only me so far." The founder depends on it daily. No one else has run it, asked for a build, or paid. This design is a bet that a populated first run converts the one or two known people into weekly users. It is not a response to observed pull.

## Status Quo

The founder's own workaround before Membrae, in their words: "markdown files, copying stuff from chatgpt or claude. reminding chatgpt or claude that im building it in cursor in order to get more appropriate responses."

So the material a new user already has is: markdown files in a repo, text pasted from chats, and context held in their head. The first run should accept exactly those inputs.

Web search (2026-10-11) adds two things. Headless MCP memory servers are a crowded field with almost no adoption (65 weekly downloads, 1 star, 13 stars on the examples found). And memory tools lose trust when an entry is wrong and the user cannot see or fix it. Membrae's edge is that it is an app where the record is visible and editable.

## Target User & Narrowest Wedge

Target user: one of "one or two" people the founder knows who plan in ChatGPT or Claude and build in Cursor. Not yet named in session. Naming them is the assignment.

The founder rejected a narrow wedge (chat-to-Cursor handoff only) and chose the full personal OS framing with Spaces as core. The narrowest version consistent with that choice: the first run produces exactly one project and exactly one Space. Not a workspace tour, not every object type.

## Constraints

- DESIGN.md window and sidebar are locked. Setup lives in the content column as a page. No new chrome, no system sheet, no second bar.
- DESIGN.md empty-state rule ("one sentence, tertiary") stays for ordinary pages. Setup is its own page, not an empty state with an illustration.
- `features/chatgpt-claude-import.md` section 2 says "There is no onboarding prompt." That line is scoped to the Import settings feature. This design adds a first run and does not put import controls in it beyond a link to Settings, so the spec stands. Confirm when reviewing.
- The app target is sandboxed (`com.apple.security.app-sandbox: true`). Reading a user's repo folder and writing an MCP entry into another tool's config both cross the sandbox.
- A model is required to run the setup agent. The user must connect one (ChatGPT plan sign-in or Cursor) before anything can be built.

## Premises

1. Membrae is a personal OS: projects plus life, for the user and their agents.
2. Spaces is core to that, not a second product.
3. The next proof is one known person running it for a week.
4. An empty app cannot demonstrate premise 1, so first run must populate it.

Premises proposed by the reviewer and rejected by the founder: that the wedge is only the chat-to-Cursor handoff, that a repo markdown file is the main competitor, that Spaces should be hidden from the first user.

## Approaches Considered

- A: Hand over the current build and watch. Ruled out: empty app, the trial may fail for a reason unrelated to the idea.
- C: Concierge setup, founder populates the app by hand before handover. Was the reviewer's recommendation (fastest test, writes the spec for B). Founder chose B instead.
- B: Self-building first run. Chosen.

## Recommended Approach

B. Six steps, in order. Each reuses something that exists.

1. Detect first run. Empty store and no completed-setup flag routes the launch tab to Setup instead of Home. No first-run code exists in the app today (searched `PersonalContext/` for onboarding and first-launch flags, found none).

2. Connect a model. One screen, two choices, using the existing sign-in paths: `ChatGPTSignIn` / `ChatGPTProvider` or `CursorProvider`. Setup cannot continue without one. State it plainly on the page.

3. Setup conversation. A chat on the solid page, driven by the existing `ChatEngine` with tools from `MembraeToolGateway`. The agent asks at most four questions:
   - What are you building right now? (drop a repo folder, or describe it)
   - Paste or drop anything you already keep for it: notes, a markdown file, a chat you copied.
   - What is one thing in your life you track or wish you tracked? (habit, job search, recipes, reading)
   - Which coding tool do you build in?
   Inputs go through `FileExtraction` and the code-root path (`ProjectCodeWorkspace`). From them the agent creates one project with tracks, decisions, and notes (`create_project`, `create_track`, `create_decision`, `create_note`), then one Space using the catalog flow already defined for agents (`get_space_catalog`, `create_space`, `set_space_type` with collection and detail screens, then a few `create_space_record` rows).

4. Review. The user sees what was built before it becomes theirs: a list of created records grouped by project and Space, each openable, each with Keep and Delete. Reuse the mark-for-deletion pattern (`features/mark-for-deletion.md`) rather than a new mechanism. This is the trust step the research points at: visible, correctable memory.

5. Connect your coding tool. One button writes the `membrae-mcp` entry into the tool they named in step 3. The app already parses MCP client JSON (`MCPJSONImport`, `MCPConnectionStore`); this is the reverse direction and is new. Then a single test: "Ask Cursor what you decided about X," with X taken from a decision created in step 3. Browser chats are one line with a link to Settings, Import.

6. Land on Home with the project pinned and the Space in the sidebar. Set the completed flag. Setup can be rerun from Settings.

States to design for each step: loading (agent working, reuse the chat wait state), partial (project built, Space failed), error (model sign-in failed, tool call rejected), and skip (user wants an empty app; allow it, one plain link).

## Open Questions

1. History ingest does not exist. The approach as first described said the agent would read imported ChatGPT or Claude history. The shipped import is the other direction: a live browser chat writes into Membrae and cannot read it, and there is no export-file reader. This design uses paste and file drop instead. Is that enough, or is a real export parser (ChatGPT `conversations.json`, Claude export) in scope?
2. Who are the one or two people, and do they use Cursor, Claude Code, or something else? Step 5 depends on the answer.
3. Sandbox. Can a sandboxed app write `~/.cursor/mcp.json`? Likely needs a user-selected file grant and a security-scoped bookmark, or a copy-to-clipboard fallback. Decide before building step 5.
4. Runner dependency. `PersonalContextRunner/runner.ts` is TypeScript. Does a fresh Mac need Node or Bun installed for Runs to work? If so, first run must either bundle a runtime or hide Runs until one is present.
5. How does the setup agent choose a Space's screens well for a subject it has one sentence about? The MCP instructions say screens must fit the subject. Needs a small eval set (five life subjects, check the screens are usable).
6. No demand evidence exists. If the first outside user completes setup and does not return on day two, the problem is the product claim, not onboarding.

## Success Criteria

Measured on the first outside user, founder watching and not helping:

- From opening the DMG to a populated project and Space in under 10 minutes.
- Their coding agent answers one question from a Membrae decision in the same sitting.
- They keep at least 80% of what the agent created at the review step.
- They open the app on 4 of the next 7 days.
- They add or edit at least one Space record themselves, unprompted, within the week.

## Distribution Plan

- Developer ID signed, notarized, stapled DMG. The project has a team ID, automatic signing, and hardened runtime already. Whether a Developer ID Application certificate and a notary profile exist is not verified.
- The `membrae-mcp` binary ships inside the app bundle so step 5 can point at a stable path.
- Release is a local script at first: archive, export, `notarytool submit --wait`, staple, build DMG. No CI yet. Hand the DMG over directly. Auto-update (Sparkle) is deferred until there is a second user.

## Dependencies

- Spaces work currently uncommitted on main (screens, record views, links, formulas, Space MCP tools) must land first. The setup agent builds a Space with it.
- A Developer ID certificate.
- Answers to open questions 2, 3, and 4.
